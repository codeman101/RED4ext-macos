# cyberpunk-gog-port

Notes and tools for running [codeman101/RED4ext-macos](https://github.com/codeman101/RED4ext-macos) on the **GOG native macOS build** of Cyberpunk 2077 2.5.0 (LC_UUID `1DFA005C-ED12-306F-B349-67BE555F2F72`, image base `0x100000000`).

Discussion and candidate tables: https://github.com/codeman101/RED4ext-macos/issues/1

## Status (unverified against the official address DB)
- RED4ext core: 21 GOG candidates, all startup self-checks pass in a debug copy under lldb.
- TweakXL: runs (TweakDB loads, 196423 records) once its own tables are patched: 21 embedded copies of the 79-entry address table, `InitializeAddressTable` immediates, and the memory-vault expected-offset table (4 pools x 5 allocator slots).
- ArchiveXL (`tools/patch_archivexl.py`): loads without crashing next to TweakXL in the debug copy. Patched: table entries matched by Steam offset (ArchiveXL lists some functions under extra hashes), the `TweakDB_Load` hook, `CBaseEngine_LoadGatheredResources` (candidate `1:0x3C4FA84`) and its own memory-vault table (35 slots, incl. PoolEngine/PoolRefCount/PoolDefault at Steam-0x20).
- ResourceDepot (hash 1704595399): GOG `0x934F518`. Found through the "Resource depot not initialized" assert string: its caller uses getter `0x41ece58` (`adrp; ldr; ret`, setter right after, 67 callers). Checked at runtime in the debug copy: the global holds an object with a binary vtable, a heap array at `+0x10` and 4 entries at `+0x1c` once the game is up. It is null early in boot, so a hook that fires before the depot exists crashes in `ExtensionLoader::Configure()`.
- ArchiveXL hook 2923109755 -> `0x252F8D4` (candidate). Tested 52 shape candidates with `dbg/hit.py` (breakpoint on the detour). 40 fire before the depot exists and crash in `ExtensionLoader::Configure()`, 11 never fire, and `0x252F8D4` is the only one that fires once, with the depot filled, and keeps the game alive for 120 s. After it, `ExtensionLoader::Load()` runs and registers more hooks. Two of them are `ResourceLoader_IssueLoadingRequestByPath` (`0x41E3ABC`, 43 insns, request built with 1 at `+0x19`, -1 at `+0x20`, 0 at `+0x28`, as the SDK note says) and `ResourceLoader_IssueLoadingRequest` (`0x41E3B68`, the next function, same `0xAC` distance as in Steam). Both now attach. With them in place `Load()` goes further and 76 more hooks fail with `Detour error -2` (list in `notes/axl_failing_hooks.txt`, Steam offsets). Game stays up for 120 s.
- ArchiveXL hook 2885423437 = `ResourceDepot_InitializeArchives` (name from ArchiveXL's own table) -> `0x3EF35A8` (candidate): exactly 241 insns and 1 caller like Steam, and it holds the "Failed to find any archives in the base data directory" assert (found by xref of that string). The hook attaches and the game stays up 100 s; not checked that it fires.
- `gameIGameSystem_Spawn*` (hash 2509382878) -> `0x515E35C` (weak candidate): 228 insns, 13 callees, 9 callers vs Steam 232/14/9, the only close shape match (`0x3e7ffd8` and `0x3be3f50` were rejected earlier). The hook attaches and the game stays up 100 s; it can only fire once entities spawn, which a menu-only run does not reach, so it is untested.
- Added since (2026-11-02/03, all by Steam->GOG layout shift, bodies mostly not checked): TweakXL +6 entries; ArchiveXL +17 (11 CharacterCustomization state/system at shift +0x50E8E8, 6 CMesh at -0xE843D8) and +6 GarmentAssembler (-0xC083C). Rejected: the 4 CharacterCustomization controller virtuals (0x4BAE148, 0x4BAF2C0, 0x4BB0AC0, 0x4BB13FC; GOG targets look like shared code and crash from the generic component tick), ItemFactory*Request LoadTemplate/LoadAppearance at shift -0xC0730 (`__stack_chk_fail`). About 55 ArchiveXL hooks, ~33 TweakXL entries and the StatService hook are still open, so those features stay off.
- Mods (debug copy, reported by the install owner): the Mac game mounts `archive/Mac/mod` by itself (ArchiveXL logs "mounted by the game, not mounted again", `lsof` shows the archives open). Plain replacement archives (clothing refits for a custom body) worked in game with no clipping. `.xl` files are read by ArchiveXL, but what they add (body type, `resource: patch`) did not show, because the appearance/resource hooks are not ported. Equipment-EX did not compile: it needs ArchiveXL >= 1.28 and Codeware >= 1.21.1, this port is 1.27.4 / 1.20.4. Do not run `engine/tools/scc` (or `launch_modded.sh`) against the real install while testing: it rewrites `r6/cache/final.redscripts`. The debug copy uses its own copy of `r6/cache`.
- TweakXL YAML (debug copy): `r6/tweaks/*.yaml` files are read and imported without errors. The TweakDB counters in the log change after import (records 196423 -> 196427, flats +110, pooled values +6 for 4 string flats), so records are created and flats written. Not confirmed visually: renaming weapons (`displayName` literal strings) was not checked in game, and adding a `VendorItem` to vendor stocks (`Vendors.wat_*_gunsmith_01`, `Vendors.WeaponVendingMachine`) did not show the items in the 2nd Amendment shop (record names guessed, `qty` not set). `quality` on a base item had no visible effect. StatService hooks are not ported, so stat-based tweaks are untestable.
- `ResourcePath_Create*` candidate `1:0x416DDE0`: exactly 107 insns (same as Steam), leaf FNV-1a 64 that strips leading quotes and slashes, 220 caller functions. Found with `tools/fnvleaf.py`. The hook attaches and the game keeps running; not checked that ArchiveXL's path mapping actually works.
- `LoadGatheredResources` candidate `1:0x3C4FA84`: virtual call `[vtbl+0x100]`, then a `bool` check whose failure path calls a helper (`0x3C530B4`) holding the "Not all Gathered Resources were loaded!" assert; the only caller function is `0x3C4EE94`. Found with `tools/callers.py`. Static only, not confirmed at runtime.
- Skipping the logos/intro to speed up test runs: `-skipStartScreen` has no effect in this build (runs with and without it end the same). The string is a `gsm::Params` session key (next to `sessionType`, `save`, `forceShutdownAfterSessionLoaded`), not a command-line argument; the only argument string found is `-jobDebugger`. `dbg/hit.py` takes extra launch arguments from `CPG_ARGS`.
- Played with it (reported by the owner of the install, not logged by tooling): on the debug copy launched through lldb (`dbg/play.py`) with RED4ext, TweakXL and ArchiveXL as patched here (Codeware ignored in that run; later runs with Codeware patched also reach the game and open Map, Inventory, Cyberware, Journal and Character menus without a crash), a real saved game loaded and played for about 5 minutes with no crash and no corrupted-data message; RED4ext shut down cleanly. The `Spawn` candidate was in place. Which ArchiveXL/TweakXL features actually worked in game was not checked.
- Signing: the original-signature binary cannot run with RED4ext (hooks rewrite game code and macOS kills the process: `SIGKILL (Code Signature Invalid)`, `Invalid Page`). The ad-hoc re-signed debug copy (`dbg/setup.sh`) works and loads/saves games; the Galaxy sign-in errors appear with or without it.
- TweakXL tweak import (2026-11-02): `TweakChangeset::Commit` crashed because the table held ~1900 entries still at Steam offsets; only those needed at boot had been ported. The job-system cluster (JobQueue/JobHandle, 10 functions) was found by matching the relative layout of the whole Steam cluster in the GOG function starts (7/7 exact, shift 0xD45798); the JobQueue global (hash 1508445968) is `0x9A2E340`, taken from the game's own `adrp/ldr` in the callers of the dispatch wrapper `0x409D8F0`. `0x409A090`, `0x409A0D0` follow from the same shift, `0x40AB57C` is only checked to be a function start. With these, a `r6/tweaks/*.yaml` import runs to `Import completed` without crashing (a clone of an existing record, a new flat, and a bad `$base` that is correctly reported as missing).
- Earlier note (superseded): the `TweakDB contains N records` line does not change with a tweak, but the import counters (records/flats/pooled values) do change, see the TweakXL YAML bullet above. `TweakDB_CreateRecord` candidate `0x2F5439C` is called from the TweakDB load path (seen under lldb). Checking the records in game still needs CET or a redscript, neither is ported.
- About 40 TweakXL table entries remain at Steam offsets (e.g. Steam `0x50F0D14`, `0x51EA4F0..`, `0x432AFF4..`, `0x4126C10`). Layout matching on small clusters is too loose to trust without a shape check per function.
- `dbg/play.py`: `BP=0x2F5439C,...` sets address breakpoints (callback counts hits; with several threads lldb may stop with `EXC_BREAKPOINT`), and on a crash it prints LR and return-address-like stack words.
- Codeware 1.20.4 (`tools/patch_codeware.py`, patched locally, not published): initialises and reaches the main menu in the debug copy (200 s, no crash). Ported by Steam offset -> GOG: Entity lifecycle group (shift `0x13348A0`), `InitEngine` `0x3C4EE94`, `ScriptValidator::Validate/ValidateProperty/CompareType` (`0x42A1970/0x42A2A78/0x42A2C50`), `ISerializable` default vfuncs (`0x41AF584..0x41AF92C`), `IScriptable::DestructValueHolder` `0x42DB400`, `ScriptBundle::~ScriptBundle` `0x4216860`, and the R30 script-loader wrapper RVA (`0x3C4A334`, immediates rewritten, so `codeware_postLoadScripts` runs). Unported entries keep the Steam value and jump into unrelated code, so every crash so far was a missing entry. Methods: struct-offset fingerprints taken from Codeware's source, vtable-slot scan of `__DATA_CONST`, constant shift from ported neighbours. Not verified with any Codeware mod or save. ~25 hooks still unported (ink group, `GetGameInstance`, `CGameFramework_InitializeGameInstance`, `ObjectSerializer_Prepare`, resource-job hooks). Later (2026-11-03): `Entity_RequestComponents` `0x2CDC8E0`; and `Mac::PatchScriptOpCodes` hard-codes the Steam opcode handler table rva `0x9A5C940` in two movz/movk pairs (patched to GOG `0x9AAEF30` in `patch_codeware.py`), without which the Character menu crashed in `ScriptOpCodeNew`. Codeware's own dylib can hold such hard-coded rvas outside its address table; check the disassembly for movz/movk pairs.
- Added 2026-11-03 by adjacency to resolved anchors (same Steam/GOG distance, landing on a function start; bodies not exercised): ArchiveXL `ResourceDepot::RequestResource` `0x3EF3BD4` and `CheckResource` `0x3EF3EB8`, `LoadArchives` `0x3EF4618`, `GarmentAssemblerState::ChangeItem/ChangeCustomItem` `0x1F47D78/0x1F48028`, `CharacterCustomizationSystem::Initialize/GetResource` `0x50D6084/0x50D640C`. They install without Detour errors and the game opens the menus and exits cleanly. Observed firing under lldb breakpoints: `LoadArchives` (9 hits), `RequestResource` (68), `CheckResource` (2), `ChangeItem` (4), and `CharacterCustomizationSystem::Initialize` reached its original through the hook trampoline during New Game. `ChangeCustomItem`, `CharacterCustomizationSystem::GetResource` and `Entity_RequestComponents` were not observed firing (not counted, not proven wrong). A new game was played through the corpo intro with inventory, character, cyberware and journal menus, a save/load and a clean exit, with no crash. Rejected: the GarmentAssembler triple at shift 0x133d160 (static init code) and `JobHandle_Wait` (unverified). `notes/axl_failing_hooks.txt` lists the ArchiveXL hooks that still fail, with names from ArchiveXL's `Library.hpp`. TweakXL's stat hooks (`StatService: Stats hooks unavailable`) remain; the hashes in the upstream `Library.hpp` are not in the installed plugin, so they cannot be named.
- Tested only on a debug copy launched from lldb, not through the normal launcher.

## Layout
- `notes/gog_candidates.tsv`: hash, name, Steam 2.5 offset, GOG candidate, confidence.
- `tools/`: static analysis scripts (`python3 -I`). `tools/patch_tweakxl.py` patches an original TweakXL 0.2.0 dylib for GOG (sha256-checked, re-signs ad hoc). `shape3.py` = shape-based function matcher.
- `dbg/`: `setup.sh` makes a debuggable copy outside the .app; `crash.py` / `trace.py` are lldb commands.
- `probe/`: read-only `DYLD_INSERT_LIBRARIES` probes (edit the log path first).

## Not included
No game binary, no patched plugin dylibs, no saves. Bring your own game and plugins; patch locally.
